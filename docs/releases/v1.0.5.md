# igni app 1.0.5

The app's half of igni's end-to-end test campaign: the findings the campaign
made against the desktop app and the web UI, fixed here.

`igni-core` (the backend, the `igni` command, the decisions service) is
released in lockstep with the app: this app installs `igni-core==1.0.5` on
first launch, and the release stops before it builds anything unless PyPI
already serves that version.

## What you get

| | |
|---|---|
| Desktop | `.dmg` (macOS), `.msi` (Windows), `.AppImage` (Linux) — under **Installers** on the release |
| macOS updater | `igni_aarch64.app.tar.gz` and `latest.json`, for an installed app that updates itself |
| Web UI | inside the desktop app. It is not a separate download, and neither igni-core nor igni server serves it; to use it in a browser, build `clients/web` and host `dist/` yourself |
| Backend | installed on first launch as `igni-core==1.0.5` |

The app starts igni's backend on its own. You do not install Python, `uv` or
`igni-core` yourself — the first launch fetches them.

## What changed

Most of this release is the app side of the campaign. The rows it opened
against the desktop app and the web UI are closed, and the fixes are the
findings themselves.

- **The window's token no longer sits in the process list.** The shell hands
  the backend its per-launch window token over a pipe (`IGNI_WS_TOKEN_FD`),
  so the token is not readable out of the backend's environment for the life
  of the process. igni-core 1.0.5 reads the pipe; an older backend is still
  given the environment variable, which every igni-core reads.
- **The AppImage starts the backend with your environment, not the AppImage
  mount's.** AppRun points `PYTHONHOME`, `PYTHONPATH` and `LD_LIBRARY_PATH`
  into its own mount, and every Python the shell started inherited them: the
  provisioned runtime could not import `igni_core`, the managed venv died
  before it signalled ready, and a fresh install never got past the loading
  page.
- **The File menu says what it did.** A refused *Reinstall Backend* names
  the reason in a dialog, a *Restart Backend* really restarts the backend and
  brings every window back with it, and *Diagnose Backend* reports the
  interpreter the app actually runs — the dev override, the provisioned
  runtime or the managed venv — instead of always the managed one.
- **Every update request goes through the update policy.** The windows no
  longer hold the updater plugin's own grant, so no page script can reach
  the network behind the policy's back, and the menu's check always answers:
  with checks off it says so, and a failed check says that too.
- **The native menu acts on the window it was used in.** *New Chat* is a new
  chat and not a new window, one window's *Check for Updates* checks once
  rather than once per window, and a release build no longer offers *Toggle
  Developer Tools*, which does nothing there.
- **Opening a file with the system app works.** The grant the windows hold
  for it now covers the files under your home folder; a file outside it still
  opens in the app's own preview, and dotfiles stay out of reach.
- **A queued message waits below the running reply and runs as its own turn**,
  instead of splitting the reply in two and gluing its answer to the tail.
- **A prompt a crash interrupted comes back with Retry and Edit prompt**, and
  one that is no longer wanted can be discarded: the backend drops the row,
  so it does not come back with the next load.
- **A tool card shows the tool's output without the model's quarantine tags.**
- **An emptied composer reads as empty**, so the up arrow recalls the history
  again once you have typed and then deleted everything.
- **The MCP page approves a project's server, and withdraws an approval.** A
  server from a project or a plugin's `.mcp.json` connects only once it is
  approved, and until now the desktop app could not ask for that approval at
  all.
- **A page's title is the window's level-one heading, a page's location is
  folded into the address bar, and an extension page's address is a link to
  it** — one you can open in any browser, on the page and at the place it
  names.
- **The sign-in dialog is drawn above the sign-in wall**, cancelling it
  closes the dialog without a "Login failed" line, and the wall takes a
  sign-in page address for a server whose portal is on a port of its own.
- **The first-run block does not offer a signed-in person another sign-in.**
- **The account chip says who is signed in**, not that it is not connected;
  the server not answering is a different thing, and the chip says which of
  the two it is.
- **The sidebar says a session is waiting, and picking it attaches it**, so
  the approval it paused on can be answered in the window that asked for it.
- **A reopened chat draws the workflow run card again.** The backend keeps
  a workflow run's card in the session's history, but the app had no reader
  for that turn, so it was read as one the app does not know and dropped: a
  session opened again showed no run card at all. The app reads the run's
  tape now and folds it into the same card the live events drew.
- **A folder picked mid-session asks "Trust this folder?"**, and a refusal
  by policy stays open until the person dismisses it.
- **A visualization the model garbled says it could not be drawn**, in the
  place of the empty card it left behind.
- **A code paste asks for its snippet under the name igni-core reads**, so a
  pasted snippet becomes a code pill.
- **The Programs panel says a revoke disconnects the programs using the
  token**, which is what the backend does.
- **An extension's 401 retry asks the backend for a new service token**, an
  open extension page follows a group's re-branding and not only dark and
  light, and a page's own `navigate` and `setLocation` reach the window.
- **The desktop app opens `igni://` links on the page and the place they
  name**, and brings its running window forward for one.
- **The released `.dmg` carries the stapled `.app`.** Tauri builds the image
  before the release job notarizes and staples the application, so the
  application inside the image had no ticket and a first launch offline
  could not pass Gatekeeper.

The accessibility work is in the same release. The window's axe spec opens
the sidebar pages and walks the slash menu, the real window passes axe and a
spec scans it in both themes, the completion menu follows its highlight and
is a listbox the editor drives, the welcome screen's command cards are
buttons a keyboard reaches, the Hooks, Watcher and Help pages pass axe,
Escape closes the account menu, and search results drop the wrappers the
snippet window cut.

The backend that comes with it (`igni-core==1.0.5`) carries three more of the
campaign's findings:

- **A workflow's agent call answers its pauses and stays out of the chat.**
- **A sub-agent spawned after `/hooks` reload fires the hooks the reload
  left.**
- **A process adopted after a restart is told ended when the window stops
  it.**

## What is still open

Eight rows of the campaign are still unproven. They need a real desktop — the
native macOS menu, the native dialogs or the WKWebView — which the session
that ran the campaign could neither see nor drive. Their fixes are in and
their tests pass; what is missing is somebody watching them happen.

- reinstalling the backend, and the refusal that names the reason;
- restarting the backend, and every window coming back with it;
- the diagnose report naming the interpreter the app runs;
- the per-launch token reaching the window over the pipe;
- the native menu acting on the window it was used in;
- the update policy refusing a request, and the menu's check saying so;
- the content security policy in the app's window;
- the Linux install — the `.AppImage`, which needs a Linux desktop to build
  and to run at all.

## Upgrading

An app installed from an earlier release updates itself: the macOS updater
reads `latest.json` and the installed app checks the payload's minisign
signature against the public key it ships with. Windows and Linux installers
are replaced by running the new one over the old.

Nothing about your settings, sessions or connections moves. They live in the
backend, and the backend is upgraded to `igni-core==1.0.5` with the app.

## Verify

`SHA256SUMS` lists every file on the release, and each one carries a build
provenance attestation and, for the desktop app, a CycloneDX SBOM
(`igni-desktop-1.0.5.cdx.json`). The full procedure — checksums, provenance
online and on an air-gapped machine, and the cosign signature once the key
ceremony has happened — is in [VERIFYING_RELEASES.md](../VERIFYING_RELEASES.md).

```bash
sha256sum --check --ignore-missing SHA256SUMS
gh attestation verify igni-desktop-installer.dmg \
  --repo ignite-ember/igni-app \
  --signer-workflow ignite-ember/igni-app/.github/workflows/release.yml \
  --source-ref refs/tags/v1.0.5
```
