# igni app 1.0.4

The first release cut from **igni-app's own repository** — the desktop app
and the web UI, and nothing else.

`igni-core` (the backend, the `igni` command, the decisions service) is its
own repository now, and the two are released in lockstep: this app installs
`igni-core==1.0.4` on first launch, and the release stops before it builds
anything unless PyPI already serves that version.

## What you get

| | |
|---|---|
| Desktop | `.dmg` (macOS), `.msi` (Windows), `.AppImage` (Linux) — under **Installers** on the release |
| macOS updater | `igni_aarch64.app.tar.gz` and `latest.json`, for an installed app that updates itself |
| Web UI | the same UI the desktop app loads, in a browser |
| Backend | installed on first launch as `igni-core==1.0.4` |

The app starts igni's backend on its own. You do not install Python, `uv` or
`igni-core` yourself — the first launch fetches them.

## What changed

This is the first release from this repository, so it carries everything the
split moved into it.

- **The repository is the app.** The backend, the CLI and the cloud layer are
  `igni-core`; the SDKs are `igni-sdk`. What is left here is `clients/tauri`
  (the desktop shell) and `clients/web` (the web client), with their own
  tooling, their own CI and their own coverage floors.
- **The app's wire contract is igni-core's, byte for byte.**
  `src/protocol/wire-schema.json` is a copy of the schema igni-core publishes,
  and a test fails while the two differ. The two halves cannot drift apart
  without the build going red.
- **One module per concern, and a test for each.** The refactor's standards
  reached the app: the shell's runtime, its windowing, its diagnostics and its
  packaging are separate modules with their own tests, rather than one large
  file.
- **The release names its own backend.** `igni-core.version` is the single
  source of truth; `scripts/sync-version.mjs` copies it into the Tauri
  config and the crate manifest, and the release refuses to run if the
  committed files disagree with it, or if PyPI does not serve that version.
- **The release notes are written down.** `docs/releases/v1.0.4.md` is this
  file, and the release workflow uses it when it exists. Without it the page
  would have carried the forty-one commit subjects between the last tag and
  this one — mostly dependency bumps.

## Upgrading

An app installed from an earlier release updates itself: the macOS updater
reads `latest.json` and the installed app checks the payload's minisign
signature against the public key it ships with. Windows and Linux installers
are replaced by running the new one over the old.

Nothing about your settings, sessions or connections moves. They live in the
backend, and the backend is upgraded to `igni-core==1.0.4` with the app.

## Verify

`SHA256SUMS` lists every file on the release, and each one carries a build
provenance attestation and, for the desktop app, a CycloneDX SBOM
(`igni-desktop-1.0.4.cdx.json`). The full procedure — checksums, provenance
online and on an air-gapped machine, and the cosign signature once the key
ceremony has happened — is in [VERIFYING_RELEASES.md](../VERIFYING_RELEASES.md).

```bash
sha256sum --check --ignore-missing SHA256SUMS
gh attestation verify igni-desktop-installer.dmg \
  --repo ignite-ember/igni-app \
  --signer-workflow ignite-ember/igni-app/.github/workflows/release.yml \
  --source-ref refs/tags/v1.0.4
```
